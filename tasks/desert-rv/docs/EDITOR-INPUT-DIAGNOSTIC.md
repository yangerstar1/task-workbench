# Editor input diagnostic candidate, not a completed playthrough

Prepared against shared `combat-contract-integration` runtime API (the matching older diagnostic export was also read). No Unity, emulator, C# compiler, or game was run for this candidate. Nothing is published or accepted. Python syntax and negative-evidence checks are the only executed checks. Review and compile in free public GitHub Actions using Unity 6000.3.19f1 before use.

## What this source actually supplies

`Runtime/Diagnostics/JourneyInputEvidence.cs` is entirely guarded by UNITY_EDITOR (including its UnityEditor imports), so it can attach an ephemeral MonoBehaviour in PlayMode but is absent from player builds. It supplies input replay and evidence collection. It drives production TouchInputState Begin/Move and existing HUD-level Begin/Pause/Restart/RetryLoad entrypoints. Session.Sample runs first, Director consumes afterwards. An explicit Editor-only replay owner supplies active finger IDs to the ordinary TouchInputState.ReconcileFingers path; held controls retain a single ID and a single Begin edge until release. Real OS input is excluded only while this owner is attached. Context changes retain ordinary cancellation/suppression: a held control must lift before a fresh press. Physics, camera movement, enemy AI, shot raycasts, five-second installations, ram contacts, storms and additive loads remain exclusively production-owned. No position teleport, state assignment, rewards, enemy damage, accelerated time or forced victory is performed.

This is logical-control replay, not OS keyboard/touch injection and not Android touch-UI validation. Directional inputs are held in real wall time, aiming is degrees/second. Each step can fail closed on region, status, control or current interaction prompt. Interaction/reload are single initial-frame edges; fire may be held. There is deliberately no guessed route or claimed successful replay.

Timeline JSONL records every frame: monotonic wall/game/storm time, actual positions, controls, health/ammo/upgrades, parts, power, gate/objective states, cabin/install/reload state, candidate approval bits as observed (never changed), prompt and load errors. Real motor ram contacts have separate events. Screenshot capture is once per wall second at end-of-frame, with PNG names and actual capture timestamps in the log. Capture requires a rendered Editor under Xvfb, not `-nographics`. The overlay always identifies diagnostic/unapproved/automated origin.

Original-speed video is captured independently from a verified dedicated floating GameView X11 window, never the desktop. The recorder refuses non-unit timeScale and nonzero captureFramerate. ffmpeg uses x11grab -window_id with 30fps and no speed filter/edit cuts. A first-real-video-frame handshake precedes the first replay input; continuous window/PID/title/visibility/dimension and GameView focus/PNG heartbeats fail closed. Actual ffprobe checks frame rate/duration against recorded capture start/end UTC. Identity verification does not grant visual/gameplay approval.

## Entry and plan contract

For manual diagnostic inspection, load the actual saved JourneyBootstrap in Editor PlayMode, explicitly open a valid scope, then start capture. Set explicit DESERTRV_INPUT_PLAN and DESERTRV_EVIDENCE_DIR; the output directory must be empty. Call StartCapture(path, directory) from a future Editor PlayMode test or the Diagnostics menu. Do not change scene state to force an expected precondition. Menu method does not itself enter PlayMode or generate scenes.

Plan fields: label, maximumWallSeconds (hard diagnostic budget), steps. Step fields: label, seconds (>0), region (0=no assertion), status/control (enum names), promptContains, moveX/moveY [-1,1], lookXDegreesPerSecond/lookYDegreesPerSecond, accelerate/brake/fire/interact/reload, command (Begin/Pause/Restart/RetryLoad), allowLoadError. No other commands accepted. Real gameplay errors stop unless the active step explicitly permits expected load errors. AllowLoadError is for negative testing only; it never marks a load successful.

Build the actual route only after rendered observation of real authored geometry. A plan is open-loop and will stop if conditions differ. Inspect the screenshot/telemetry, adjust honest control durations/aim, and replay; never repair a failed run by modifying state. A plan ending is explicitly not success. Failure remains failure. A synthetic pilot is always labeled automatic.

## Rendered public Actions execution candidate

`run_rendered_diagnostic.sh` refuses environments without GITHUB_ACTIONS=true and GITHUB_REPOSITORY_VISIBILITY=public (the workflow supplies github.event.repository.visibility). It starts Xvfb and actual Unity without -batchmode, -nographics or -quit, using the existing licensed/free-public Actions setup. No Unity execution or billing change happened during preparation.

JourneyRenderedDiagnosticRunner.Run opens the saved bootstrap and enters PlayMode. After domain reload it opens the pinned diagnostic scope, creates a separate floating GameView via EditorWindow.ShowUtility, assigns a unique DESERTRV_GAME_<guid> title, and writes its own Unity PID/title to a fresh private handshake directory. `capture_game_window.py` searches only an exact unique visible X11 title; verifies _NET_WM_PID, /proc/PID/exe against the explicit Unity executable, map state and landscape dimensions; binds that single window ID; and captures it with ffmpeg -window_id. No fallback to whole-screen/main Editor/console is implemented.

The capture worker publishes ready only after ffmpeg reports an actual encoded video frame. Only then does the Editor start input replay. Window identity, visibility and size are checked every 0.1 seconds; loss stops capture and prevents video export. The Editor also rejects focus loss, a changed GameView object/title, stale capture heartbeat, portrait view, batch/Null graphics, or missing end-of-frame PNGs (10s startup, 5s subsequently). At termination the Editor leaves GameView alive until the capture worker drains ffmpeg and acknowledges stopped. This establishes first-input coverage and avoids recording the window's later destruction/reuse. Source verification is explicitly not artistic approval.

Unity's internal GameView type/native Linux title behavior and the installed ffmpeg x11grab window_id capability still need actual first-run verification. If any is unsupported, capture stops with a fixed failure receipt; no screenshots/video/compilation from this path are claimed to exist yet. The runtime helper files are fully UNITY_EDITOR-guarded and absent from player builds. No audio is captured; summaries explicitly state audioCaptured=false.

The first actual run must be an observed minimal 30–120 second segment (start, drive, park/exit, then observed pickup), not a guessed 1800-second plan. Default maximumWallSeconds is 120. Forty minutes in the shell is only the outer failure watchdog. Exit zero means orderly orchestration, never gameplay acceptance.

## Public evidence export boundary

All Unity/activation/Xvfb/ffmpeg logs and raw timeline remain private runner diagnostics. The reviewed workflow may upload only the explicit safe-export directory, never a workspace/log glob. `prepare_safe_diagnostic_export.py` validates every source file/ancestor against symlinks, verifies PNG CRC/full decoding/expected dimensions/nonblank pixels using the existing environment-evidence thresholds, and checks frame uniqueness/order plus finite nonnegative monotonic times. It requires verified game-window provenance, the actual video hash, ffprobe 30fps/average fps/duration, identity-monitor cadence, and capture start/end wall-time agreement.

Only after all checks succeed does it stage game PNGs, game-window video, numeric/known-category summary and SHA receipts, then atomically rename the complete directory into place. Raw exception strings, file paths, scope data, timeline, editor logs and unfiltered ffprobe metadata are never exported. Failure exposes only a separate fixed-string status receipt, with no partial success directory. There is no human-reviewed=true escape or prerequisite: reviewers can inspect source-verified game-only footage after delivery, and artistic/gameplay approval remains false.

Twelve pure Python fixture tests passed: valid atomic allowlist, duplicate frame, NaN/reversed time, blank/CRC-broken image, file/ancestor symlink, invalid source identity, changed video, late validation/no partial output, and raw metadata exclusion. Fixtures mock ffprobe and use synthetic PNG/video bytes; these test export policy only and are not Unity/video acceptance evidence.

## Acceptance matrix and stopping conditions

Main successful generation: actual region order 1→2→3; top-down driving; parked exit; first-person pickup under reach/occlusion checks; physical cabin entry and uninterrupted >=5s ram installation; return to driver; forward swept ram-gate contact above threshold; actual scene load preserving resources/storm. Then scrapyard RV proximity/power connection, real firing/reloads/wave defeats, coil acquisition and five-second install; night beacon powered defense, disconnect, drive into physical safe volume.

Separate negative scenarios: pause while driving, reload, installing, defending and loading; verify no simulation progress and released held controls. Repeated pickup/install/power interaction/restart must not duplicate resources or resurrect stale callbacks. Blocked exit/obstructed shot/remote power socket must fail naturally. A deliberately missing region name in a separately labeled test fixture should produce actual loader error and same-ticket retry; restoring loader configuration is fixture setup, never outcome mutation. Keep production scene assets untouched.

Storm: reach exposure using ordinary movement or wait in explicitly labeled failure test. Verify constant world-front speed and health loss while driving, walking, and physically inside cabin; death must lead to Failed. Use actual Restart action and establish region 1, zero upgrades/parts, baseline resources, fresh generation and original storm position. Long waiting in this negative scenario is excluded from meaningful-content duration.

Fail and retain evidence on load error, missing/placeholder model, lost director, invalid precondition, inconsistent state, blocked path, non-unit clock, exception, exhausted action budget, or unauthorized source/hash changes. Do not retry an action forever or skip a region. No APK acceptance follows from editor evidence. Landscape Android still needs real emulator/device input and performance evidence.

`check_playthrough_evidence.py` is a deliberately strict preliminary suite inspector: requires a completed generation, physical region order/driving/walking, pickup/install/ram/power/safety evidence plus failure/reset/pause/load-error/storm scenarios, images and separate video. It reports raw playing/stationary time. Its numerical pass cannot approve art, meaningful content, Android, video provenance or damage causality; these need independently reviewed evidence. Scripts must not treat gameplayAcceptance=false as approved.

## Duration/content finding

Current authored offsets are 0/100/200, allowed routes 30–100m and car topSpeed=11m/s. PoweredEncounterState resets chargedSeconds for each wave. Current authoring specifies two waves per powered region, so 28/36 seconds per wave imply minimum powered totals of 56/72 seconds, not 28/36 per whole region. No observed run yet establishes 20–30 minutes. Three short areas, two installs and these charge timers are not evidence of that goal. Expand meaningful exploration, decisions, varied encounter geometry/objectives and resource pressure, then measure active play. Never stretch waits, storm travel, charge times or walking distances solely to hit 20 minutes. Current production telemetry's OnFoot bucket can contain standing; raw Playing duration is not meaningful-content duration. New diagnostic samples separately record nearby active threats, current/completed waves, alive enemies and charge progress. Evidence buckets distinguish threatened actions/stationary exposure, driving traversal, walking exploration candidates, physical installs, reloads, empty powered waiting, idle standing and non-playing states. These are observations, not a claim every movement is meaningful exploration.
